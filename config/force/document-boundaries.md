# 产出文档的边界声明与审查

## 文档边界

本文维护文档生成、更新与审查共用的内容归属、边界声明和验收规则，适用于说明、规范、需求、计划及分析报告。文档类型的具体职责由对应技能维护，项目内的实际分工与权威入口由目标文档说明；目录、格式、保存与授权等通用约束沿用 [AI 协作约束](collaboration-rule.md)，本文不重复定义。只约束已授权的文档工作，不因此新建文档或扩大审查范围。

## 写入文档

- 长期维护文档默认在开头设置“文档边界”章节，写明主要用途、负责维护的事实或规则，以及容易混入但应由其他文档承载的内容。
- 结合实际文档关系注明权威来源、深入阅读入口及变更时应更新的位置。只链接已确认存在的来源；尚无独立承载文档时说明当前归属，不编造链接或为凑分工新建文档。
- 短文档、一次性报告和薄入口可将边界并入开头的用途或范围说明；报告同时说明对象、时间或版本范围，避免快照被当成长效规范。
- 已有“职责”“用途与范围”等同等说明时直接补全，不重复加章；保存或局部更新已有成果时沿用原结构和确认状态，不为补边界扩写或重排；范围外缺口在交付中报告。固定机器契约或用户指定格式优先，在允许的说明位置表达边界。
- 声明必须针对本文的具体职责，不能照抄“避免重复、明确边界”等写作要求。区分文档内容归属与业务功能范围，两者不能互相替代。
- 仅供生成时读取的规则提示、占位符和本机路径不写入面向项目读者的业务文档。

## 开发阶段文档与归档

- 需求闭环、需求文档、开发计划、开发留痕及阶段核查/验收记录是对应需求和时点的开发材料，不作为长期事实文档维护。长期规范、架构和操作指南不得依赖这些材料定义当前事实或建立持续关联引用；有效的当前规则和机制由所属长期正文维护，阶段材料本身无需因此删除或重写。
- 上述开发阶段文档中只要出现完整连续文本 `归档状态：已归档`，即默认视为已归档历史文档。后续更新相关功能时，不再同步更新其正文、进度、链接或验证结果，不因代码或长期文档变化重新校准其历史内容。
- 标记按上述原文精确匹配，不用“已完成”“已归档”等近似措辞、文件日期或目录名推断；没有该标记不代表它是长期事实文档，也不代表可自动归档。不得为文档整理批量添加归档标记、删除阶段材料或改变未决状态。
- 用户明确要求修订或解除归档时才按指定范围处理；归档文档可用于用户要求的历史追溯，但不能替代当前代码、有效规范及所属长期事实正文。

## 共用声明骨架

首次生成或获准补全边界时使用以下骨架；统一的是用途、维护内容和关联内容归属，不固定标题、句式或章数。将占位内容替换为目标文档的具体事实，已有等价说明直接复用。

### 持续维护文档

```markdown
## 文档边界

本文面向{读者}，用于{用途}，维护{本文负责的事实或规则}，适用于{对象或目录范围}。
{容易混入的相关内容}由{已存在的权威文件或来源入口}维护；本文保留{读者需要的摘要或引用}。
```

“职责与边界”“用途与范围”等已有章节可以承载上述内容；README 可并入导语和文档导航，薄入口可用一句话说明负责的入口指引及权威正文位置。关联内容确由本文维护时明确当前归属；没有独立文档时不编造分工、链接或额外交付物。

### 分析与审查报告

```markdown
用途与归属：本文记录{分析或审查对象}的{结论、证据及适用的处理状态}；{长期规则或其他专题内容}由{已存在的权威入口}维护。
范围与时点：{对象、代码/版本或采样范围、检查时间}；{实际证据与未验证限制}。
```

报告可将上述内容并入“结论与范围”或概览；已有范围、时间、版本和证据字段直接复用。范围或版本未知时如实说明，不能把生成时间当作检查时间，也不能用快照结论替代长期契约。简短对话结论按实际需要在范围说明中表达，不强制套用完整文档骨架。

## 内容取舍与验收

- 判断内容是否直接支持本文读者理解、决策或操作；仅与主题相关不足以成为收录理由。
- 同一规则或事实保持明确的权威维护位置，其他文档使用引用和必要摘要。保留自足理解与执行所需的上下文，不把 README、操作指南或完整分析压缩成链接目录。
- 交付前核对产物中的用途、维护内容和关联归属是否具体、入口是否真实，再对照正文检查越界展开、重复定义、无用途填充或本职责必需信息的遗漏；不能以技能或模板外已有声明、或存在章节标题代替产物的语义核查。
- 审查问题应指出具体内容、影响及建议归属。既有文档没有独立标题但边界清楚时，不单凭标题缺失判错；只审查时给建议，不擅自改写。
