# AI 协作约束（通用红线）

## 回复用户时

- 使用简体中文，命令、代码、日志和文件原文除外

## 准备改代码时

- 检查最近一次 `git pull` 时间；超过 2 小时执行 `git pull --rebase`，成功后更新时间再改
- `git pull` 冲突或失败时，先解决同步问题
- 最近一次 `git pull` 操作时间：2026-09-12 15:39:09 CST
- 注意：内容要写入到项目的AGENTS.md，此文档这里为`模版`

## 需要先确认时

- 涉及技术方案、交互设计或关键实现决策时，先给推荐选项和理由，确认后再开发
- 业务规则不确定时，先确认，不得写死

## Git 提交时

- 执行 `git commit` 前，必须先使用 `git-commit-msg` 技能基于确认范围生成提交消息
- 不得跳过 `git-commit-msg` 技能自行临时编写提交消息

## 建文档目录时

- 默认放 `./agent-works/`，落盘前按“所属模块、本次需求”做一级归属判断
- 一级名用`{module-slug}`、`{change-slug}` 表示模块及其需求或改动，使用小写 kebab-case，并表达业务含义
- 属于已有模块时复用 `./agent-works/{module-slug}/`；新增的独立需求、局部功能或专项改动放入该模块的 `{change-slug}/` 子目录。仅在不属于已有模块时新建一级业务目录
- 同一需求的开发计划、留痕、业务核查、SQL等文档复用同一最终目录

## 写文档时

- 在写技能、规范/约束类文档时，只沉淀最新事实和稳定规则，优先抽象出通用不变量。更不要留下过程说明、自我注释等非抽象的流水账内容
- 非用户明确或主动调用技能所要求时，不得新建属于开发过程的阶段性文档

## 写代码时

### 复用/规范
- 新增或修改前先参考同类实现，优先复用现有的能力
- 保持项目现有布局、UI、目录、命名、分层、返回结构、异常处理、日志、权限校验和配置方式；偏离时说明原因
- 改动清晰、克制、易扩展；避免无必要的新依赖、新抽象、过度封装和硬编码；公共逻辑按既有方式沉淀
- 方法、实体、类等关键代码必须有必要的注释说明，满足人工可读性
- 改动后必须要检查对应的改动会影响此功能的其他能力或相关关联的功能
### 性能/安全
- 考虑数据量、调用频率、事务范围、查询复杂度、缓存影响、资源释放和重复计算
- 避免 N+1 查询、大对象一次性加载、重复远程调用、无限增长集合、阻塞式长任务和资源泄漏

## 写页面时

- 涉及界面风格、组件、样式、布局、主题、设计 token 、视觉统一、品牌一致性或设计优化时，必须遵守 `DESIGN.md` 相关要求；需要高质量界面生成或避免模板化输出时，可启用 `frontend-design`
- 后端、接口、数据库、脚本、测试、构建、部署、性能、安全等非 UI 任务，不启用 `frontend-design`，不读取 `DESIGN.md`

## 写SQL时

- 涉及数据库变更、初始化数据、字典、菜单、权限、配置或迁移 SQL 时，写清 SQL 文件路径、用途、执行时机、影响范围、回滚方式或不可回滚原因
- SQL 默认命名为 `{sql-purpose}.sql`
- SQL 文件必须有注释、包括总体、字段、执行语句的注释，说明用途、影响范围、前置条件、回滚方式或不可回滚原因”

## 写注释时

- 优先用命名和结构表达意图，不写复述代码的低价值注释
- 复杂业务规则、状态流转、权限边界、兼容逻辑、性能取舍、异常兜底、外部系统约束必须注释

## 做测试时

- 所有代码改动先自审，再在能证明风险的最低层执行最小验证；默认不跑全量测试、完整构建或多视口 E2E
### 前端
- 文案、注释、说明和不改变运行逻辑的展示属性只做差异与格式检查；纯函数、状态计算、接口和领域规则使用对应的定向测试
- 页面临时查看、点击、截图或控制台检查优先使用 AI 工具内置浏览器；未获用户明确要求，不连接其个人 Chrome、Edge 或其他外部浏览器
- Playwright 等长期 E2E 只用于低层测试无法覆盖、稳定且高价值的浏览器关键链路；局部交互、样式、文案和一次性缺陷不新增 E2E
- 完整构建只在构建配置、依赖、路由或懒加载、全局资源、发布产物受影响，项目明确要求，或用户要求时执行；源码未再次变化时不重复运行同一验证
### 后端
- Java 改动后必须执行项目的编译测试，如果改动的功能业务复杂则还要加入对应单元测试
