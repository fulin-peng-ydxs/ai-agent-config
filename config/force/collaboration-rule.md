# AI 协作约束（通用红线）

## 文档边界

本文维护跨项目的协作、复用、文档、测试及提交底线；项目具体命令、业务口径和设计契约由项目入口与事实文档维护，更具体的项目规则和用户明确要求优先。文档边界细则见 [文档边界声明与审查](document-boundaries.md)，页面验证共用流程见 [前端验证规范](frontend-verification.md)，本文保留触发条件和引用，不复制专项流程或项目事实。

通用底线变更更新本文，专项规则更新对应规范，项目特例留在项目文档；不保存会话流水、阶段验收或临时环境信息。

## 回复用户时

- 使用简体中文，命令、代码、日志和文件原文除外

## 读取规范时

- 从任务适用的全局、项目与专项入口定位权威规则；源码和配置用于核实实现事实，现有代码、历史惯例或记忆不能自动覆盖有效规范
- 入口缺失或规则冲突时，先查已声明的替代来源，并按运行环境的指令层级、明确的优先级和适用范围处理；不得自行选择较宽松的规则或编造要求
- 仍无法确定且影响正确性、授权或验收时，说明缺口及影响，暂停依赖该结论的操作；不受影响的工作继续，缺失部分不得宣称合规或验收通过

## 准备改代码时

- 先核对目标仓库、当前分支、上游及工作区（含暂存改动）。非 Git 项目不执行同步；没有上游或处于 detached HEAD 时不猜测远端或切换分支，说明当前同步条件
- 有上游时检查最近一次成功 `git pull` 的时间；超过 2 小时或没有有效记录，执行 `git pull --rebase`。存在未提交改动时先判断能否安全同步，不得为同步擅自 stash、覆盖、丢弃已有工作或重写已共享历史
- 同步失败或发生冲突时，保护已有改动，先解决同步问题再改代码；无法安全处理时报告阻塞，不用旧时间或仅 fetch 成功冒充同步完成。没有上游且任务需要远端基线时，先明确基线再实施依赖它的改动
- 仅在成功 pull 后，将实际时间、时区、仓库及分支记入目标项目 Git 忽略的 `.local/last-git-push`；该文件记录 pull，不以文件修改时间或上次 push 时间代替

## 需要先确认时

- 需求或业务规则的歧义影响正确性、可行方案在范围/架构/兼容性/成本上有实质分歧、拟操作超出既有授权，或适用专项流程要求人工确认时，先完成可独立推进的调研和准备，形成可审阅的具体内容，再请求决定；不确定的业务规则不得写死。各技能维护专项确认节点，本文统一维护确认渠道、答复效力及授权复用，不因使用交互工具新增审批节点
- 人工确认默认通过当前 AI 工具提供的审批、确认或结构化问询能力完成；先核实其可用性及用途限制，有可用且适用的工具时必须使用，不以普通对话代替。展示待决定内容、对象和范围，按决定需要说明身份、具体差异、影响、验证及回退，提供适用的继续、取消或调整选择；需要选择方案时给出推荐及理由
- 工具未提供、用途受限、策略禁用或调用失败时，说明具体原因，再回退为同范围的对话确认并等待明确答复；用户明确限定只能使用工具审批时，暂停依赖动作，不自行降级。不假定某产品必有特定接口，不擅自修改权限配置来制造弹窗或规避审批
- 平台执行权限与任务方案批准分别核对：平台权限使用其原生授权机制，方案或范围确认仅使用用途允许的交互能力。方案批准和对话确认不能代替平台授权；平台未授予执行权限时停止相关动作，不绕过工具或环境限制
- 用户已确认的方案和授权在其有效范围与期限内持续有效；范围内的常规实现选择自行处理，不因技术细节、技能内部调用、换工具、重连或会话切换重复索要同一授权，也不为弹窗再次申请已有批准。新信息改变目标、身份、范围、方案前提或实质风险时，只确认新增差异
- 授权依据须来自可信用户消息或人工审批回执，并覆盖本次决定的对象、范围及适用版本。提交申请、工具调用成功、默认选项、关闭弹窗、超时、沉默，以及 AI 写入的方案或“已确认”标签、文件已保存或被下游引用，均不能单独充当批准；用户明确批准且覆盖本次差异的成果可以作为依据。适用流程要求留痕时，在已有记录中关联真实答复、申请渠道和有效范围，不为普通问询另建审批文件
- 未取得必要答复前暂停依赖该决定的操作，继续不受影响的工作；拒绝、撤销或授权失效后停止相关动作，要求人工决定的节点不能由自动决定替代

## Git 提交时

- 执行 `git commit` 前，必须先使用 `git-commit-message-authoring` 技能基于确认范围生成提交消息

## 建文档目录时

- 相对路径以目标项目根目录为基准；当前工作区不是目标项目时，先定位目标项目，无法确定时再询问
- 需长期保留的文档默认放 `./agent-works/`，落盘前按“所属模块、本次需求”做一级归属判断；临时过程产物按下节处理
- 一级名用`{module-slug}`、`{change-slug}` 表示模块及其需求或改动，使用小写 kebab-case，并表达业务含义；避免仅用日期、随机数、`new`、`v2` 等弱语义后缀
- 属于已有模块时复用 `./agent-works/{module-slug}/`；新增的独立需求、局部功能或专项改动放入该模块的 `{change-slug}/` 子目录。仅在不属于已有模块时新建一级业务目录
- 同一需求的开发计划、留痕、业务核查、SQL等文档复用同一最终目录

## 生成临时产物时

- 临时产物指执行、排查或验证中，AI 主动生成且无需交付或仅供一次性使用的截图、脚本、测试数据、调试日志、临时下载/解压文件、渲染/转换中间文件、草稿/备份等，不得提交 Git
- 目录按以下优先级选择，生成前明确输出路径并按任务隔离：
  1. 用户明确指定或项目已约定的临时目录：遵循对应约定
  2. 项目根目录已有 `.local/`：存入 `./.local/tmp/ai-agent/{task-slug}-{unique}/`，集中存放项目内临时产物
  3. 项目没有 `.local/` 或无项目：存入 `$TMPDIR/ai-agent/{project-slug}/{task-slug}-{unique}/`；`TMPDIR` 未设置时使用系统默认临时目录（如 Linux/macOS 的 `/tmp/`、Windows 的 `%TEMP%`），无项目时 `project-slug` 用 `projectless`
- 项目内临时目录须被 Git 忽略；除用户或项目明确约定外，不得散落到源码、文档或其他项目目录
- 正式交付物及需维护的源码、测试、文档、运行资源按用户或项目约定存放；不得仅为展示、引用方便将临时验证产物转为长期资源。长期文档、运行代码不得依赖临时文件；提供临时链接须注明位置及可能被清理

## 写文档时

- 区分新交付物与持续维护文档：明确要求新建或独立需求所需的文档按归属目录新建，不覆盖已有成果；更新规范、事实、索引或同一成果的修订时维护既有权威文件，不另建平行定义。不得仅因存在同类文档就用新需求覆盖旧内容
- 生成、保存、更新或重构文档时，读取 [文档结构与输出规范](document-output.md)；创建、重构或审查自有技能同时读取当前技能目录的 `skill-authoring-standard/SKILL.md`
- 长期维护的说明、技能和规范只保留当前有效事实与稳定规则和内容，不保留写作过程、自我评价和无关历史
- 需求闭环、需求文档、开发计划等开发阶段文档不作为长期事实文档维护，长期文档不与其建立持续关联引用；保留阶段材料，不因文档整理删除、重写或批量添加归档标记
- 开发阶段文档含完整匹配文本 `归档状态：已归档` 时，默认作为历史存档，后续功能变更不再同步更新其正文、进度、链接或验证结果；不以近似措辞、日期或目录名推断归档，用户明确要求修订或解除归档时除外
- 生成、更新或审查文档时，读取并遵守 [文档边界声明与审查](document-boundaries.md)，由其统一维护内容归属、权威位置和边界声明要求
- 非用户明确要求或主动调用的技能所要求，不得新建开发过程中的阶段性文档

## 写代码时

### 复用规范

- **查入口**：修改前读取适用规范并检索同类实现，定位共享入口；以有效规范为准，不照搬已有违规写法
- **用入口**：已有适用能力必须直接消费；不足时先使用既有扩展点或扩展共享入口，禁止复制或在消费方重写同类能力
- **新增门槛**：无适用入口时才新增；同职责能力第二次出现须收敛到共享入口，确因语义、生命周期或分层边界不能合并的，说明依据。遵守项目结构与编码约定，避免无必要的依赖、抽象和硬编码
- **查消费方**：共享改动须追踪受影响的使用点，清理已迁移的重复实现并验证；交付说明复用入口及必要例外。规范变更须反查并消除旧规则冲突

### 性能安全
- 考虑数据量、调用频率、事务范围、查询复杂度、缓存影响、资源释放和重复计算
- 避免 N+1 查询、大对象一次性加载、重复远程调用、无限增长集合、阻塞式长任务和资源泄漏

## 写页面时

- 涉及界面风格、组件、样式、布局、主题、设计 token 、视觉统一、品牌一致性或设计优化时，必须遵守 `DESIGN.md` 相关要求；需要高质量界面生成或避免模板化输出时，可启用 `frontend-design`
- 前端按结构、状态/交互、样式/token、工具分别核对复用；只套共享组件外壳、内部另写同类逻辑或状态样式，不算完成复用。已有共享规则的差异通过其属性、插槽、配置或变量表达；使用相同 token 不等于复用了状态配方
- 后端等非UI/页面改造任务，不启用 `frontend-design`，不读取 `DESIGN.md`

## 写SQL时

- 涉及数据库变更、初始化数据、字典、菜单、权限、配置或迁移 SQL 时，写清 SQL 文件路径、用途、执行时机、影响范围、回滚方式或不可回滚原因
- SQL 默认命名为 `{sql-purpose}.sql`
- SQL 文件必须有注释、包括总体、字段、执行语句的注释，说明用途、影响范围、前置条件、回滚方式或不可回滚原因

## 写注释时

- 方法、实体、类等关键代码或关键的配置信息必须有必要的注释说明，满足人工可读性
- 优先用命名和结构表达意图，不写复述代码的低价值注释
- 复杂业务规则、状态流转、权限边界、兼容逻辑、性能取舍、异常兜底、外部系统约束必须注释

## 做测试时

- 所有代码改动先自审，再在能证明风险的最低层执行最小验证；默认不跑全量测试、完整构建或多视口 E2E
- 根据本次变更检查测试与门禁的覆盖缺口；已有能力直接复用，覆盖不足时补充或更新相关测试。规范约束已有检查器时，契约变化同步维护检查器及合法、违规样例；同职责的新增检查优先扩展既有入口。无适用检查器时，仅在规则可稳定自动判断，且存在重复执行需求或明确的确定性收益（如高风险误操作防护）时新增，并接入既有执行入口；一次性低风险文档或措辞修改可用差异检查和定向走读验证，不附带建设新门禁。按风险执行适用验证，报告结果及未验证项；必要检查未通过或未执行，不得宣称验收通过
- 不得仅为获得通过而删除或弱化断言、扩大豁免、跳过检查或降低规范以迁就违规实现。确有契约变更、测试错误或合理例外时，说明依据，按实际影响维护规则、检查器与正反例；修正测试或检查器不等于需要放宽规范，调整后仍须拒绝应拦截的违规
- 验证涉及服务状态时，先记录原运行状态及恢复所需的模式、参数和环境，不记录密钥。优先使用项目既有服务脚本；原本运行则结束后恢复原运行方式并检查健康，原本停止则保持停止，用户另有要求时除外。需要加载本次改动时按既有授权安全重载或重启；恢复失败须报告实际状态及未完成项，不得宣称完成

### 前端

- 不影响布局与行为的文案、注释、说明和展示属性只做差异与格式检查；纯函数、状态计算、接口和领域规则使用对应的定向测试
- 改动影响页面呈现或操作可达性（如布局、尺寸、滚动、定位、弹层、响应式或内容显隐）时，必须在受影响范围内完成浏览器实测；无法实测时明确未验证范围，不宣称页面验收通过
- 页面验证的场景选择、证据与完成条件统一读取 [前端验证规范](frontend-verification.md)。项目具体契约与各技能专项标准仍由原入口维护，不在各处复制共用验证流程
- 页面临时查看、点击、截图或控制台检查优先使用 AI 工具内置浏览器；未获用户明确要求，不连接其个人 Chrome、Edge 或其他外部浏览器
- Playwright 等长期 E2E 只用于低层测试无法覆盖、稳定且高价值的浏览器关键链路；局部交互、样式、文案和一次性缺陷不新增 E2E
- 完整构建只在构建配置、依赖、路由或懒加载、全局资源、发布产物受影响，项目明确要求，或用户要求时执行；源码未再次变化时不重复运行同一验证

### 后端

- Java 源码、依赖或构建配置改动后，使用项目既有命令执行适用的编译校验；涉及行为变化、缺陷修复或边界风险时，补充或更新必要测试并执行定向回归，不以“业务是否复杂”决定是否验证
- 分别说明编译与测试结果；跳过测试的编译或打包命令不能证明测试通过，未执行的测试及其影响须明确报告
